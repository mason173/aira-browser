# WebApp Back Exits The WebApp Session

Accepted: Aira WebApps use the same Back ordering as ordinary Web pages while Web content can consume Back, but once transient Web UI and Web history cannot consume Back, the terminal outcome is explicit WebApp Exit rather than Browser Home or default system Back. Aira should consume that terminal Back, save WebApp state, and close the current WebApp UIAbility/window through an owned exit path. WebApps are also single-surface sessions: target-blank/window-open intent and automatic Web navigation stay in the current WebApp surface by default, including out-of-scope links. Login, OAuth, payment, verification, and other return-sensitive WebApp transaction flows must not be handed to the normal browser; ordinary browser tabs can still use parent, adjacent-tab, and Browser Home fallback behavior.

Accepted: desktop Web entry has one Aira product behavior. "As app install" is the product label for creating an Aira-owned simulated PWA container; it is not a real system/PWA install and not a PWA installability chooser. Manifest availability may improve metadata such as title, icon, start URL, scope, theme color, or display hints, but missing or incomplete manifest must not downgrade the entry into a separate browser-like shortcut mode. The internal `web_shortcut` mode should be deleted rather than preserved as a compatibility path.

Accepted: relaunching a desktop WebApp should restore the last recorded `currentUrl` when available. The install/start URL is only the fallback target. This keeps the simulated PWA container aligned with the user's app-like expectation: leaving and later reopening returns to the state they were using.

Accepted: WebApp new-window intent remains in the WebApp session. Ordinary `_blank` / new-tab intent loads in the current WebApp surface. Popup flows that require Web return channels such as opener or postMessage must still be owned inside the WebApp session, not exposed as user-visible Aira-syncs and not handed to the normal browser.

Accepted: WebApp terminal Back has a dedicated owner. `BrowserMainBackCoordinator` should route unavailable Web Back for an active WebApp session to `WebAppExitCoordinator`. That owner consumes Back synchronously, deduplicates an in-flight exit per window, performs a short best-effort flush of the committed/restorable current URL, terminates the current WebApp UIAbility/window, and clears WebApp session/presentation state only after platform termination succeeds. A termination failure must leave the running WebApp session intact so Back can be attempted again. `BrowserShellPage.ets` only supplies shell facts, presentation side effects, platform execution, and diagnostics hooks.

Accepted: an attached ArkWeb controller failure during system Back is diagnostic only. It must not display a technical retry/exit prompt or use failure counts and time windows to trigger WebApp exit. The current WebApp remains active and a later Back follows the normal history path again; only an unavailable history root exits immediately.
