# User Script Value State Has One Commit Owner

Accepted, 2026-07-21; amended 2026-08-07: `UserScriptValueStateStore` is the single owner of device-local GM value readiness, schema, monotonic revision, global mutation ordering, batching, committed state, and Incident lifecycle. Its production persistence seam has committed-byte read, optional previous-copy read, and whole-file replacement operations, implemented by one HarmonyOS file adapter. Before replacing an established current file, the adapter writes and synchronizes its last committed bytes to `values.json.previous`; it then writes and synchronizes `values.json`, and Native Bridge acknowledges success only after that current write finishes. A current document may maintain a provisional synchronous view, but native reads, new documents, listeners, and runtime snapshots observe committed revisions only.

Only confirmed absence of both current and previous files is first-run state and creates an empty current-schema snapshot. On startup, the Store owns decoding and schema validation for both candidates. A valid previous copy restores an interrupted or invalid current write; if neither candidate is valid, the adapter preserves both and only user-script execution is blocked. The rest of browser startup continues and User Script management exposes the redacted failure stage/code. Runtime commit failure keeps the previous synchronized snapshot available, rejects the affected batch, and opens one redacted Incident until a later successful replacement proves recovery. Store-level failures and recoveries are retained as a bounded diagnostic history without script identity, URLs, keys, or values. There is no user-facing Reset workflow.

## Considered Options

- Preferences fallback was rejected because multiple production writers would create multiple meanings of persistence ACK.
- Per-script writers or queues were rejected because cross-script ordering and snapshot revision would no longer have one owner.
- Old-schema migration and partial salvage were rejected. An unreadable or unsupported snapshot fails closed instead of being rewritten, preserving the only data copy for a later explicit recovery decision.
- A manual temporary-file overwrite rename was rejected because Huawei's checked SDK documents the API but does not guarantee crash-atomic replacement of an existing file. The previous copy makes process-termination recovery independent of that undocumented behavior.
- Script-specific reload interception was rejected because it compensates for failed persistence outside the owning module and cannot provide durable ordering.

## Consequences

The current schema is intentionally strict and has no legacy compatibility path. Capacity rejection is distinct from a persistence Incident. Whole-file replacement uses the device-proven direct file API because `AtomicFile.startWrite()` was rejected by the target device. Direct writes call `fsyncSync` before close; the previous copy doubles worst-case Value State disk usage and write volume but remains untouched while the current file is replaced. A current file interrupted by process termination can therefore fall back to the last complete revision without relying on undocumented rename atomicity. Future sharding or cross-document listener broadcast may replace internals behind the same owner, but must preserve one committed revision authority and one production persistence meaning.

## Disabled Script Startup Readiness

Amended, 2026-10-24: Execution readiness must not load retained script packages, GM value files, or journals when all scripts are disabled. `UserScriptRepository` owns a small startup hint in a separate Preferences instance. Only a supported hint explicitly recording no enabled scripts permits the cold-start shortcut; missing, malformed, or unknown hints require reading the authoritative package settings. A successful settings read refreshes the hint. Existing installations therefore read package metadata once before gaining the shortcut, without loading disabled scripts' GM state.

The hint is a disposable optimization, not a second settings authority. Every package-settings write durably invalidates it before writing the payload, then refreshes it after the payload is committed. An interrupted write can require extra work on the next launch but must never hide an enabled script. No shortcut deletes or rewrites retained package or value data. Huawei documents Preferences instances as cached after their first file read and `flushSync()` as persistence of cached changes; the separate small instance and write ordering are Aira engineering choices ([Preferences reference](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-data-preferences)).

Enabled scripts still wait for the existing Value State owner before document-start injection. Installing, restoring, updating, or enabling an executable package also waits for that owner before publishing the enabled package. Management and installation surfaces load authoritative metadata on demand before listing packages, checking duplicates, or mutating them. Execution initialization coalesces concurrent calls but rechecks later enable/install transitions; runtime diagnostics use their independent initializer and do not hold first-paint readiness.

The executable regressions are `scripts/check-aira-userscript-startup.cjs` and `scripts/check-aira-userscript-lazy-sessions.cjs`. They exercise the production owners with deterministic platform storage boundaries, including retained disabled data, legacy hint creation, failed writes, re-enabling, and delayed surface initialization. Host timings are not measurements of phone launch latency.

## Isolated Deletion and Prepared Script Reuse

Amended, 2026-11-03: The Store supplies the target script identity, committed revision, and timestamp to the isolated adapter when deleting a package. The adapter removes only that script from its already committed snapshot and durably updates the manifest before acknowledging deletion; unrelated GM payloads do not cross the boundary as a serialized aggregate. Failed manifest writes leave the Store and package list unchanged. The shared-document persistence fallback retains its existing whole-document contract.

Document-start preparation may reuse an existing artifact before rebuilding its value snapshot when the committed Store revision, script inputs, and bridge token are unchanged. A changed revision still checks the script's current snapshot, including when another script caused the revision change. Failed commits cannot publish provisional values through this cache, and source changes, token rotation, private-mode exclusion, and package deletion continue to invalidate the affected artifacts.

## Bounded Journals, Bulk Bridge Operations, and Package Payloads

Amended, 2026-11-03: An existing script's journal is compacted when its next append would exceed 1 MiB. The adapter writes and verifies the new isolated snapshot before removing the journal. The verified snapshot is the commit point: cleanup failure is deferred, not reported as a failed mutation. Replay skips journal revisions already covered by the base snapshot, so interruption between snapshot publication and journal cleanup cannot restore stale values. The global Store remains the sole mutation-order and acknowledgement owner.

`GM_getValues` / `GM.getValues` and `GM_setValues` / `GM.setValues` each have a dedicated native route. A bulk read or write crosses the bridge once and receives the same token, grant, enabled-state and URL validation as a single-value operation. Bulk writes use one provisional command and one Store commit; a serialization or validation failure rejects the entire request. Synchronous bulk reads fetch only missing keys. Document-end preparation does not build a GM snapshot that its lazy runtime would discard; explicit snapshot consumers keep their existing committed-state contract.

Installed package settings now use a version-2 small Preferences index. `UserScriptPackageStorage` owns immutable per-package files containing source, dependency source and resources. New payload files are written, fsynced, closed and read back before the repository publishes the index. Metadata-only changes reuse existing files. Legacy settings are validated, materialized and replaced by the index only after every referenced payload is durable; failure retains the old authority. Missing or invalid indexed payloads fail closed. Startup-hint invalidation still precedes index publication, and repository mutations are serialized across asynchronous payload writes.

After index acknowledgement, retired payload cleanup is best-effort. On the next validated open, only unreferenced files with the owner's generated filename format are collected; interrupted unpublished writes are therefore reclaimable. Cleanup is ordered before subsequent payload preparation. The layout changes the on-disk package schema, not the exported backup schema. Huawei documents file read/write byte counts and `fsync`; immutable payloads plus an acknowledged Preferences index avoid relying on replacement-rename guarantees ([file API reference](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-file-fs)).

The startup replay also covers bulk request counts and authorization, provisional rollback, bounded journal replay, interrupted compaction cleanup, failed package migration/update, orphan recovery, and concurrent package mutations. Byte/work counts are host regression evidence; user-visible latency is measured separately on a device.

## Indexed Reads and Per-Script Artifact Invalidation

Amended, 2026-11-03: Committed GM reads use a script/key index, published at the same durable boundary as the Store document. Runtime snapshots and management projections traverse only the requested script. Admission and provisional mutations never update that index; failed writes retain the previous index. Transition and unchanged-timestamp calculation use temporary identity maps instead of nested full-document searches, preserving transition order and value equality semantics.

Prepared document-start artifacts now compare the requested script's committed value revision, rather than the global revision. Another script's commit therefore does not rebuild or hash an unchanged large snapshot. The Store still owns one monotonic global revision for persistence and bridge acknowledgements. Empty scripts use an in-memory `-1` cache token, distinct from valid imported revision-zero data, so clearing the last value invalidates the artifact without retaining deleted-script revision entries.

Native URL matching reuses up to 512 recently used compiled patterns, including invalid-pattern results. Each global/sticky regex starts at index zero on every check. Bulk script matching parses the target URL once; rule edits, excludes, compatible URLs and grant checks keep their existing behavior. Regression replays measure compilation and traversal counts and check native/Web matcher parity, cache eviction, commit failure, synchronous commits, deletion and recreation.
