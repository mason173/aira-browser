# Quick Search Switching Is Native Session Chrome

Accepted: 2026-07-24

## Context

Quick Search Switching lets a user compare one Aira-submitted query across the configured Search Engine Roster without changing the Default Search Engine. The surface must coexist with ArkWeb navigation history, top-chrome immersion, fullscreen, Web runtime discard, private browsing, and a Web viewport that must not be covered. ArkWeb exposes BackForwardList indices and item fields but no stable history-entry identifier or place to attach application metadata.

## Decision

Quick Search Switching is native ordinary-browser top chrome below the system safe inset and above Web content. When eligible it occupies layout height rather than overlaying the webpage or treating the safe inset as spare control space. Its visibility projects from the existing top-immersion owner, so scroll-driven hiding, always-top-hidden mode, fullscreen, and WebApp eligibility do not acquire a second policy owner.

`BrowserQuickSearchSwitchingCoordinator` is the single non-page owner of tab-local process-session context, exact-engine switch commands, and presentation projection. Formal Search Submission seeds it with the query and effective routed engine; `BrowserWebPageLifecycleApplicationCoordinator` remains the sole ordinary Web Navigation Transaction owner and supplies typed navigation/history facts; `BrowserWebTopImmersionSessionCoordinator` remains the top-visibility owner. The ArkUI row only renders projected state and forwards actions, while `BrowserShellPage.ets` is limited to mounting, binding, and one-line forwarding and must shrink if implementation touches it.

Context is not persisted across process death and is never reconstructed by parsing URLs. Same-process Back restoration uses app-owned correlation between navigation transactions and ArkWeb BackForwardList indices or snapshots. When that correlation cannot prove that an entry belongs to the Aira Search Result Context, the feature fails closed by hiding and releasing its layout height.

The implemented enablement flag is stored by `QuickSearchSwitchPreferencesRepository` as one default-enabled device-local preference shared by ordinary and private browsing. It deliberately does not enter `SearchEngineSettings` or the frozen Personalization Sync snapshot. The live ordered engine projection always comes from `SearchEngineRepository.listEngines()`; removing the currently selected engine leaves the page unchanged and may leave the row with no highlighted item until another roster engine is chosen.

The occupied row height is 48vp. `BrowserWebViewportCoordinator` adds that conditional height to the visible top-chrome inset, `BrowserWebTopImmersionSessionCoordinator.refreshVisibleInset()` reapplies an already-visible inset, and the existing immersion/fullscreen/WebApp policy remains authoritative. `BrowserWebTopChromeOverlay` replaces the former page-owned safe-area overlay composition and renders the opaque row plus its Web-content divider; `BrowserShellPage.ets` only binds projected state and forwards engine selection.

History correlation records the ArkWeb current index, list size, and current-item URL for every committed owned result. Back/Forward and History API changes restore only an exact retained association; History API initialization is ignored, and an unassociated `pushState`, `replaceState`, or `popstate` hides the surface. ArkWeb may report a regionalized final result URL through `onNavigationEntryCommitted` before it reports `onPageBegin`; while an Aira-owned switch is pending, the owner may therefore commit that pending context when the typed callback says main-frame new-entry, not same-document, and not replacement, the callback URL exactly equals the current ArkWeb history item, and the URL is not an exact known superseded target. During the same owned document-initialization window, an additional typed main-frame new-entry Commit with `didReplaceEntry=true` may rewrite the already-associated current entry only when its ArkWeb history index and list size are unchanged and its association generation is still current. This covers engines such as Google that regionalize the result and then replace that same entry with an initialized URL. Both cases use navigation-transaction evidence only: the feature still never parses an engine host, query, or final URL to reconstruct context. A `replaceState` emitted while an Aira-owned result document is still initializing may likewise rewrite that same pending or associated history entry when its old URL exactly matches the owned navigation chain and ArkWeb's current snapshot exactly matches the new URL; this narrow initialization window closes at Web load completion, so later webpage-owned searches, filters, pagination, and route changes remain unowned and hide the surface. A later unowned navigation hides immediately and cannot be restored by an old snapshot while it remains in flight; the existing Web load and history-command owners explicitly report a load that was not issued or an uncommitted load cancelled by Back, after which the feature restores only the exact still-current association. The first growth from 49 to 50 ArkWeb entries retains and updates provable associations; only a subsequent append at the already-full 50-entry boundary is treated as an ambiguous index rollover and clears them. Explicit engine taps build the selected engine template directly, bypass Smart Search Fallback, create no additional Aira search-history use, and let ordinary committed Web navigation supply the browser-history entry.

## Considered Options

- Overlaying the row on Web content or placing controls inside the system safe inset was rejected because it would cover webpage content or misuse system-reserved space.
- Reusing `SearchEngineSelectionCoordinator` was rejected because that path owns persistent or session Default Search Engine selection, while quick switching must affect only the current search.
- Making the feature a second Web navigation or immersion owner was rejected because it would split existing browser lifecycle narratives.
- Reconstructing context from result URLs was rejected because redirects and webpage-owned searches make URL inference unreliable and contrary to Aira's ownership boundary.

## Consequences

Implementation changes the statically guarded Web viewport contract by adding conditional occupied top-chrome height. It therefore requires honest guard updates and proportional phone validation for fixed-bottom pages, Bing results, scrolling immersion, fullscreen restoration, rotation, and split-screen resizing. History correlation must also be verified for redirects, Back/Forward traversal, forward-list truncation, the 50-entry list bound, reload, runtime discard, and load failure. Window-Open/BFCache may evolve through normal in-scope work; Sync retains its separate contract and verification rules.

The user accepted this feature's Web viewport-contract change on 2026-07-24. The architecture guard now pins conditional inset ownership, the extracted top-chrome renderer, exact-engine URL construction, and non-page history correlation. The separate Window-Open/BFCache static guard must continue to pass.
