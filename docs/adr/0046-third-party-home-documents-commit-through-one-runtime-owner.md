# Third-party home documents commit through one runtime owner

Accepted, 2026-07-16; amended after ArkWeb capability validation: imported HTML/ZIP homepages and URL-backed homepages share one Third-Party Home Document Runtime owner. Local and remote loading are two source adapters behind that owner, not parallel runtime architectures. The runtime owns desired, staged, committed, active, inactive-resident, failed, offline, and evicted document generations; source preparation orchestration; commit eligibility; bridge authority; navigation containment; fallback; residency execution; and one structured diagnostic timeline. Repository ownership remains limited to the homepage catalog, selection, and per-home preferences; the browser-wide background resource owner decides eviction policy; `BrowserShellPage.ets` mounts ArkUI/ArkWeb slots, forwards events, and renders published state; the tabs scene only consumes committed/resident facts.

A Third-Party Home Document Commit atomically grants one complete Browser Home presentation its interaction and bridge authority: selected source identity, document generation, appearance and privacy context, system search and entry policy, scroll behavior, bridge capability, and online/offline status. Commit does not imply a Surface replacement. Imported HTML/ZIP uses one visible real ArkWeb node from generation binding onward; while that node is staged it is non-interactive and has no bridge authority, and commit changes authority without detaching, replacing, or covering the node. URL-backed homepages retain non-visible staging and attach only when the current generation commits. A stale or mixed-generation document can never commit or obtain authority.

Imported HTML/ZIP activates only as an Aira-Prepared Third-Party Home Document. The local adapter preserves the original import and package-relative behavior, prepares an Aira-owned entry before activation, and fails unavailable rather than falling back to the raw `file://` source. Its real `FrameNode` is attached to the Home `NodeContainer` as soon as the generation is bound and stays continuously mounted through staging, commit, active, and inactive-resident states. Browser Home does not put an import preview, native cover, or second Web Surface in front of it. Arbitrary URL-backed homepages stage in a separate non-visible Web runtime and may commit after Third-Party Home Visual Readiness: current appearance is applied and the staged result is non-blank and visually stable. This does not claim that arbitrary third-party business initialization has completed. An Aira-compatible homepage may provide a stronger readiness signal. A qualified last-known-good URL-backed document may re-enter the normal staged-to-committed flow as an explicitly labeled offline document; raw cached HTML never bypasses commit.

Generation concurrency is latest-desired-wins. Source, source-content version, appearance, effective forced-dark state, privacy context, or explicit refresh creates a new generation. Older results may contribute diagnostics but can never commit, activate the bridge, publish cache state, or mutate Browser Home. Only the current committed generation may request Aira-owned interaction. A visibly mounted imported generation remains limited to readiness until commit; URL-backed staging remains non-visible. User-requested destinations leave Browser Home through the ordinary browser navigation owner while the committed homepage becomes inactive-resident; main-document replacement creates a new staged generation instead of mutating visible Home content.

Committed third-party Home remains resident during ordinary browsing and tabs overview, then becomes inactive-resident while hidden. The runtime calls ArkWeb `onInactive()` and per-controller media pause, releases keyboard ownership, rejects permission/file-selector/dialog-style interaction at the Home seam, and revokes all interactive Aira bridge authority. ArkWeb does not provide per-Web JavaScript timer suspension, so arbitrary page JavaScript, background requests, and WebSockets may continue; Aira does not describe this state as a complete freeze. Returning Home calls `onActive()` and resumes media on the same runtime, preserving DOM and scroll state when ArkWeb keeps it alive. One browser-wide background resource owner arbitrates memory pressure and may evict a misbehaving or expensive Home runtime. Private Browser Home always uses the Aira-owned native homepage until ArkWeb exposes or Huawei confirms a profile isolation model stronger than the current shared incognito context.

Cold start loads a lightweight Third-Party Home Launch Snapshot before the first ArkUI presentation so Browser Home knows the selected source, content version, target appearance, native chrome preferences, prepared-local availability, and eligible fallback metadata before it renders. For an imported homepage, Home holds its startup surface while tabs restore and immediately mounts the real prepared ArkWeb node; there is no preview capture, image handoff, native cover, Web replacement, or detach/reattach at document commit. The native Home composition layer starts at opacity `0` and scale `0.9`, then waits for both the initial page-show signal and the current custom document commit before animating the same mounted node to opacity `1` and scale `1` over 400ms with `cubic-bezier(0.2, 0, 0, 1)`. The animation changes only composition properties and does not reload, remount, or mutate Web content. The runtime exposes a small event-ingress and published-state interface rather than returning imperative `shouldLoad`, `shouldSync`, `shouldCancel`, cache, or reveal plans to the page. Native system-search, system-entry, and scroll-hide preference changes may use a presentation-only commit on the current document; source, content, appearance, effective forced-dark, and privacy changes require a new document generation.

The runtime must emit a structured per-generation lifecycle and the shipping-blocking `policy_home_document_contract_violation` guard for uncommitted visibility, invalid bridge authority, mixed-generation presentation, stale eligible-state violations, or commit bypasses. The existing `policy_background_contract_violation` remains mandatory. This decision does not change the frozen Window-Open / BFCache contract in ADR-0040.

## Considered options

- Keep raw `file://` or direct URL navigation and patch the first frame with document-start JavaScript, `onPageEnd`, `onPageVisible`, opacity, visibility, or a sibling cover over an already-visible Web. Rejected because those mechanisms do not give Aira ownership of the first visual frame and have already produced intermittent cold-start flashes. Non-visible staging remains valid for URL-backed sources, but imported prepared documents use their one real visible node from generation binding onward.
- Destroy the third-party Home runtime on every navigation away and capture a fresh screenshot for return. Rejected because it adds repeated capture/reload work, loses DOM/scroll state, and is unnecessary once the regular runtime can remain inactive-resident.
- Claim that inactive-resident means JavaScript is frozen. Rejected because Huawei's SDK explicitly says `onInactive()` does not pause JavaScript and `pauseAllTimers()` is global across WebViews.
- Maintain separate local-home and remote-home runtime flows. Rejected because lifecycle, generation, commit, bridge, failure, navigation, residency, and diagnostics are the same Browser Home responsibility; duplicating them would recreate policy drift.
- Treat `onPageEnd` or `onPageVisible` as arbitrary remote-page semantic readiness. Rejected because Aira cannot know when third-party asynchronous or business initialization has completed.
- Let `BrowserShellPage.ets`, the tabs scene, bridge module, cache module, and runtime coordinator jointly apply execution plans. Rejected because the interface would continue exposing implementation ordering and the user-visible flow would have no single narrative owner.

## Consequences

Implementation uses a home-specific ArkWeb node and visible NodeContainer slot independent of ADR-0040 protected Hosted Web paths. Every desired document generation materializes a distinct `Web`, `WebviewController`, BuilderNode, NodeController, component identity, and JavaScriptProxy bridge; generation changes dispose the previous runtime rather than updating its BuilderNode config. Imported generations attach that node immediately and keep it mounted; URL-backed generations attach after commit. Native callbacks, navigation containment, bridge/script responses, and timeout/failure work retain that immutable generation identity. Remote load failures publish the native custom-homepage failure state directly; the runtime does not automatically persist or replay HTML snapshots. Private third-party Home remains disabled, so per-private-profile isolation is not an implementation dependency. Migration must shrink the current custom-home logic in `BrowserShellPage.ets`, fold activity/bridge authority into the runtime owner, keep source acquisition, bridge protocol/action, Repository, tabs scene, and browser-wide resource policy as narrower owners or subordinate modules, and preserve the ADR-0040 window-open guard.
